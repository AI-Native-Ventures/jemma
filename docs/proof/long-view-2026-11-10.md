# P52a Long view proof, 10 Nov 2026

## Result

The `long_view.requested` event ran for each of the 5 seeded learners in a fresh `start` sandbox on a local agent worker (port 8755, `AI_MODE=cache`). All 5 events settled as `done` on the first attempt. 4 of them asked the model once. Sipho has no pattern in his records, so code saved an empty list and the model was not asked. The 4 answers are now stored in `ai_replays`.

A second fresh `start` sandbox ran the same 5 events with the worker in `AI_MODE=replay`. All 5 settled as `done`, with zero replay misses and zero model calls. Every learner got the same saved patterns as in the first run. So the prompt reaches the model the same way in every sandbox: no ids and no date of the day change what the replay key is made from.

Real time for one update, from the event row being made to `finished_at`: about 30 seconds with a model call, about 6 to 8 seconds without one. The rules page asks for about 10 minutes per update, so that number can be shortened to "under a minute" for this model on this day. Free models are slow and uneven, so treat it as one measurement.

## Run setup

- Supabase project: `jemma-dev` only. Two synthetic `start` sandboxes (one per run), both deleted when the run ended.
- Worker: local `wrangler dev` on port 8755, local queue, run through `POST /events` with the shared secret, as the web app does.
- Model: `LLM_PROVIDER=openrouter`, `LLM_MODEL=nvidia/nemotron-3.5-super-vl:free`. `LLM_MODEL_FALLBACKS` was left empty for the run, so a failure could not fan out to a second model and the call count stayed bounded.
- Cap: at most 15 model calls were allowed for the packet. To count them exactly, a temporary counter was put around the raw provider model inside the retry layer (so retries count too) with a hard stop at 15. It logged one line per real provider call. The counter was not committed and `packages/profiling/src/ai/models.ts` is unchanged in the branch.
- Driver: `packages/profiling/scripts/long-view-proof.ts`. It makes the sandbox, queues one event at a time, waits for it, then reads the saved patterns.

## What the data shows in the later demo stages

The long history is in every stage, but this year's marked answers join it. In the `marked` stage (checked with a fresh sandbox, not saved anywhere) Amina's latest fractions term is Term 4 of this year at 67%, so her struggle in fractions no longer ends at the latest term and code finds no fractions pattern for her. Her shapes strength is still found. The other four learners keep the same patterns they have in `start`. That is the rule working as designed ("a run must end at the family's latest term with data"), not a data fault, but a screen that shows the Long view after the marking step will not show Amina's fractions pattern. If it was saved earlier, the next `long_view` run deletes it when it is still a draft and switches it off (`active = false`) when the teacher has already touched it.
