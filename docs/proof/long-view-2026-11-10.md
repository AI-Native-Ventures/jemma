## Result

The `long_view.requested` event ran for each of the 5 seeded learners in a fresh `start` sandbox on a local agent worker (port 8755, `AI_MODE=cache`). All 5 events settled as `done` on the first attempt. 4 of them asked the model once. Sipho has no pattern in his records, so code saved an empty list and the model was not asked. All 6 settled as `done`, with zero replay misses and zero model calls, and every case saved the same patterns as in the first run. So the prompt reaches the model the same way in every sandbox: no ids and no date of the day change what the replay key is made from.

Real time for one update, from the event row being made to `finished_at`: 18 to 68 seconds with a model call (the case with two newer terms was the slowest), 6 to 9 seconds without one. The rules page asks for about 10 minutes per update, so that number can be shortened to "about a minute" for this model on this day. Free models are slow and uneven, so treat it as one measurement.

## The rule behind the sixth event

A pattern needs 3 or more terms in a row that all meet the threshold. It may be followed by 0, 1 or 2 newer terms with data for the same family. Those newer terms did not continue it (better than a struggle, or weaker than a strength), and they come back in `since`, oldest first, each with its percent and its sources. With 3 or more newer terms with data, the pattern is not a candidate. The stored pattern keeps the newer terms after the run's terms in `terms`, each flagged `since: true`, and their sources are part of the evidence. This way one different result, or two, does not hide a pattern that held, and the teacher sees the newer results next to it. The prompt (`jobs/long_view.md`) tells the model to say first what held and over which terms, then plainly what the newer results show, naming the test or term, with no praise and no prediction.

The rule changed the model's input twice, so the earlier recordings (4 answers, then 5) were thrown away and everything below was recorded again with the final prompt. Those 9 old rows are still in `ai_replays` under keys nothing asks for any more.

## Run setup

- Supabase project: `jemma-dev` only. Two synthetic `start` sandboxes (one per run), both deleted when the run ended.
- Worker: local `wrangler dev` on port 8755, local queue, run through `POST /events` with the shared secret, as the web app does.
- Model: `LLM_PROVIDER=openrouter`, `LLM_MODEL=nvidia/nemotron-3.5-super-vl:free`. `LLM_MODEL_FALLBACKS` was left empty for the run, so a failure could not fan out to a second model and the call count stayed bounded.
- Cap: at most 15 model calls were allowed for the packet. To count them exactly, a temporary counter was put around the raw provider model inside the retry layer (so retries count too) with a hard stop. It logged one line per real provider call. It was not committed and `packages/profiling/src/ai/models.ts` is unchanged in the branch.
- Driver: `packages/profiling/scripts/long-view-proof.ts`. It makes the sandbox, queues one event at a time, waits for it, then reads the saved patterns. For the sixth event it first adds two class tests to Amina's marks: Class Test 1 in Term 3 of the class year (3 of 4 fractions answers right) and Class Test 2 in Term 4 (4 of 4 right).

Once this year's work adds a third newer term, her struggle stops being a candidate: the next `long_view` run deletes a draft pattern, and switches off (`active = false`) one the teacher has already touched.
